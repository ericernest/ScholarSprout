# 论文精读剩余功能实现报告

> 日期: 2026-07-22  
> 范围: KG 一次性构建、KG 驱动问答、`start_reading` 上下文增强、Skill Python 后处理、后端接口适配  
> 说明: 本次实现后，论文精读仍使用单一 `POST /paper_reading` action 协议；前端方案见 `论文精读-前端接口与展示方案.md`。

## 1. 实现概览

本次完成了四组核心后端能力：

1. KG 构建从“按章节渐进构建”改为“整篇论文一次性构建完整 KG，阅读时按阶段渐进展开”。
2. 新增完整 KG 驱动问答引擎，返回自然语言答案、推理路径、证据节点和 Cytoscape 可视化数据。
3. 增强 `start_reading` 上下文，Agent 现在能看到论文元信息、目录、当前章节正文、阅读进度、已展开 KG 摘要和 active skills。
4. 补齐 8 个论文精读 Skill 的 Python 后处理逻辑，统一输出 `skill_outputs`，并给出可写入 KG 的候选节点。

同时修正了 Web/API 通道适配问题：

- `channels/web.py` 在 `mode="paper_reading"` 时保留完整请求体。
- 带 `action` 的首次论文精读请求不再强制要求前端提前提供 `session_id`，会生成 envelope session id。

## 3. KG 构建实现方式

### 3.1 构建策略

新策略是：

```text
PDF 上传/首次阅读
  -> 加载整篇论文 metadata + sections + references
  -> LLM 一次性抽取完整 KG
  -> 如果 LLM 不可用或输出不可解析，使用启发式兜底抽取
  -> 将完整 KG 写入 KnowledgeGraphEngine
  -> 保存到 storage kg/{paper_id}_kg.json
  -> 阅读时按 current_section 的阶段返回 revealed_kg
```

也就是说，系统内部保存的是完整图谱，前端看到的是当前阶段允许展示的子图。

### 3.2 LLM 输出格式

`build_full_paper_extraction_prompt()` 要求 LLM 返回：

```json
{
  "nodes": [
    {
      "ref": "method:main",
      "node_type": "Method",
      "label": "方法名",
      "section_id": "sec:3",
      "read_stage": "method",
      "properties": {},
      "confidence": 0.8
    }
  ],
  "edges": [
    {
      "source_ref": "problem:main",
      "target_ref": "method:main",
      "edge_type": "motivates",
      "label": "研究问题驱动方法",
      "read_stage": "abstract",
      "properties": {},
      "confidence": 0.8
    }
  ]
}
```

允许的 `read_stage`：

- `abstract`
- `introduction`
- `method`
- `experiment`
- `conclusion`
- `general`

### 3.3 阶段展开规则

`get_revealed_subgraph(paper_id, current_section)` 根据当前章节分类决定可展示阶段：

| 当前阶段 | 可展示 KG |
|---|---|
| `abstract` | abstract |
| `introduction` | abstract + introduction |
| `method` | abstract + introduction + method |
| `experiment` | abstract + introduction + method + experiment |
| `conclusion` | abstract + introduction + method + experiment + conclusion |
| `general` | 全部 |

返回结构：

```json
{
  "paper_id": "...",
  "current_stage": "method",
  "allowed_stages": ["abstract", "introduction", "method"],
  "nodes": [],
  "edges": [],
  "node_count": 8,
  "edge_count": 6,
  "cytoscape_elements": []
}
```

## 4. KG 驱动问答实现方式

新增 `paper_reading/kg/query.py` 中的 `KGQueryEngine`。

数据流：

```text
POST /paper_reading {action: "kg_query", ...}
  -> paper_reading.handler._handle_kg_query()
  -> 确保 paper_id 对应 KG 已构建
  -> KGQueryEngine.answer()
     -> 从 question 中抽取关键词
     -> 匹配 KG 节点 label/properties
     -> 收集相关边和邻域路径
     -> 收集 evidence 节点
     -> 有 LLM 时基于 KG evidence 生成答案
     -> 无 LLM 时生成确定性兜底答案
     -> 返回 Cytoscape 子图
```

返回结构：

```json
{
  "question": "ProtoNet 为什么比 MAML 好？",
  "answer": "基于当前知识图谱，可以这样理解：...",
  "reasoning_paths": [
    {
      "source_id": "...",
      "source_label": "ProtoNet",
      "source_type": "Method",
      "relation": "outperforms",
      "relation_label": "...",
      "target_id": "...",
      "target_label": "MAML",
      "target_type": "Baseline",
      "properties": {},
      "paper_id": "..."
    }
  ],
  "evidence": [
    {
      "node_id": "...",
      "label": "...",
      "node_type": "Experiment",
      "section_id": "sec:4",
      "summary": "...",
      "properties": {}
    }
  ],
  "matched_nodes": [],
  "cytoscape_elements": []
}
```

## 5. `start_reading` 上下文增强

`start_reading` 现在会构造如下上下文给 Agent：

```text
[论文元信息]
- paper_id
- title
- authors
- abstract

[阅读状态]
- session_id
- current_section
- active_skills
- progress

[论文目录]
- section_id: title

[当前章节正文]
标题: ...
正文: ...

[已展开知识图谱摘要]
阶段、节点数、边数、节点列表、关系列表

[用户问题]
用户原始 content
```

这解决了旧实现中 Agent 只能看到 `当前章节 + 用户问题`、无法真正精读论文正文的问题。

`start_reading` 返回新增字段：

```json
{
  "data": {
    "context": {
      "paper_loaded": true,
      "kg_mode": "full_paper_once_progressive_reveal",
      "active_skill_ids": ["reading.method_analyst"]
    },
    "revealed_kg": {},
    "kg_build": {
      "section_type": "existing|full|missing",
      "new_nodes": 0,
      "new_edges": 0
    }
  },
  "kg_update": {},
  "skill_outputs": []
}
```

## 6. Skill 后处理实现方式

### 6.1 统一行为

所有 Skill 后处理都遵循：

```text
Agent text
  -> extract_json_object()
     -> 直接 JSON
     -> Markdown ```json 代码块
     -> 文本中的首尾 JSON object
  -> make_skill_output()
  -> 返回 SkillOutput-like dict
```

输出结构：

```json
{
  "skill_id": "reading.method_analyst",
  "skill_name": "方法论分析师",
  "trigger": "auto|manual|fork",
  "output_type": "method_pipeline",
  "content": {},
  "rendered": "Markdown 展示文本",
  "kg_candidates": {
    "nodes": [],
    "edges": []
  },
  "parse_status": "parsed|raw_text"
}
```

### 6.2 各 Skill 的额外处理

| Skill | 后处理重点 |
|---|---|
| Method Analyst | 从 `pipeline` 生成 Module KG 候选节点 |
| Critique Agent | 从 `weaknesses` 生成 Limitation KG 候选节点 |
| Math Verifier | 从 `formula` 生成 Concept KG 候选节点 |
| Code Reviewer | 解析代码复现报告 |
| Domain Expert | 从 related work/positioning 生成 RelatedWork KG 候选节点 |
| Writing Coach | 解析写作模式和模板 |
| Idea Generator | 从 idea cards 生成 Insight KG 候选节点 |
| Cross-Paper Linker | 解析 research landscape |

当前后处理先返回 `kg_candidates` 给前端和后续流程消费，没有自动把所有候选写入 KG，避免把未审核的 LLM 输出直接固化。

### 7.5 获取已上传 PDF 文件

本次新增 HTTP GET 路由，用于前端 PDF.js 或 `<iframe>` 从后端恢复显示用户上传的原始 PDF。

请求：

```http
GET /paper_reading/uploads/{paper_id}.pdf
```

响应：

- 成功：`application/pdf` 文件响应，文件名为 `{paper_id}.pdf`。
- 未初始化 storage：`503`
- 文件不存在：`404`

实现位置：

- `gateway/app.py`: 新增 `paper_reading_upload_pdf()`。
- 底层调用 `PaperReadingStorage.get_upload_path(paper_id)`。

前端用途：

```js
const pdfUrl = payload.data.pdf_url;
pdfjsLib.getDocument(pdfUrl);
```

或：

```html
<iframe src="/paper_reading/uploads/{paper_id}.pdf"></iframe>
```

建议优先使用 PDF.js，因为它能提供文本层、页码定位、公式/段落选区和高亮能力。

响应核心：

```json
{
  "status": "ok",
  "action": "kg_query",
  "data": {
    "answer": "...",
    "reasoning_paths": [],
    "evidence": [],
    "matched_nodes": [],
    "cytoscape_elements": []
  }
}
```

## 9. 剩余注意事项

- LLM 抽取质量取决于模型配置；无模型时启发式 KG 是可用兜底，不等同于高质量语义抽取。
- `skill_outputs[].kg_candidates` 目前不自动写入 KG，建议前端提供“确认写入图谱”或后端增加审核策略后再固化。
- PDF 解析依赖 PyMuPDF；目标运行环境必须安装 `PyMuPDF`。
