# NoviceSynapse 论文精读模块分析报告

分析范围：仅分析论文精读模块，未修改任何源码。  
主要阅读路径：`gateway/static/paper-reading/*`、`gateway/app.py`、`handlers/paper_reading/*`、`skills/*`、`runtime/agent_runner.py`、`agents/profiles.json`、`tools/builtin/*paper*/*kg*`。

## 1. 当前前端的具体组织形式

论文精读前端是一个原生 HTML/CSS/JavaScript 单页工作台，不是 React/Vue 组件化项目，也没有前端构建链。核心文件如下：

- `gateway/static/paper-reading/index.html`：页面骨架，包含论文导入区、工作台、阅读区、右侧 Copilot、底部知识图谱、Fork 弹窗。
- `gateway/static/paper-reading/styles.css`：论文精读专用样式。
- `gateway/static/paper-reading/app.js`：几乎所有前端业务逻辑都集中在一个文件中。
- `gateway/static/app.js`：全局页面效果/公共脚本，被论文精读页一并引入。

页面分成两个大状态：

1. Intake 导入区：上传本地 PDF、从 URL/arXiv 导入、搜索论文并导入。
2. Workbench 工作台：左侧导航与进度，中间阅读器，右侧 Copilot，底部知识图谱。

工作台内部的组织形式：

- 左侧 `navigator-panel`：论文标题、作者、标签、阅读进度、章节目录、8 个 Skill 开关、暂停/恢复/刷新进度按钮。
- 中间 `reader-panel`：两个阅读模式。
  - “论文重排”：`structured-reader`，用后端返回的 `paper.sections` 渲染章节、段落、公式样式和图像。
  - “PDF 原文”：`pdf-reader`，本质是一个 iframe，加载 `/paper_reading/uploads/{paper_id}.pdf#page=...`。
- 右侧 `copilot-panel`：主分析流、Skill 输出卡片、Fork 分支 tab、提问输入框。
- 底部 `kg-panel`：知识图谱 SVG 展示、KG 查询表单、节点详情和证据/推理路径。

前端状态集中在 `app.js` 顶部的 `state` 对象，包括：

- `sessionId`、`paperId`、`paper`、`pdfUrl`、`hasPdf`
- `currentSection`、`progress`
- `activeSkills`、`skillOutputs`
- `revealedKgElements`、`queryKgElements`、`selectedNode`
- `selectedText`
- `forks`、`activeFeedId`
- `kgMaxStageIndex`

前端持久化只使用 `localStorage` 保存少量状态：session id、paper id、当前章节、结构化阅读滚动位置、右侧栏宽度。刷新后前端会先尝试恢复 session，再加载 paper detail。

接口组织上，前端所有论文精读写操作和查询操作都统一调用：

```text
POST /paper_reading
```

请求体用 `action` 区分动作。前端统一封装在 `callPaperReading(body)`，它会自动补入当前 `session_id`、`paper_id`、`content`、`metadata`，并解析 gateway 返回的 envelope。

## 2. 论文精读部分的数据流、前端如何返回信息给后端、已实现功能和 LLM agent 技术

### 2.1 总体数据流

核心链路如下：

```text
前端 app.js
  -> fetch POST /paper_reading
  -> gateway/app.py: paper_reading()
  -> gateway/message_flow.py: process_channel_input()
  -> handlers/paper_reading_handler.py
  -> handlers/paper_reading/handler.py 按 action 路由
  -> pipeline / storage / session / kg / agent / skill postprocessor
  -> 返回统一 JSON envelope
  -> 前端 applyReadingPayload()/对应 render 函数更新 UI
```

后端在 `gateway/app.py` 启动时注入了一批共享对象到 `app.state`：

- `paper_reading_agent`
- `paper_storage`
- `kg_engine`
- `kg_builder`
- `kg_query_engine`
- `session_manager`
- `fork_manager`
- `paper_pipeline`
- `tool_registry`
- `skill_registry`
- `capability_selector`

`handlers/paper_reading/handler.py` 是论文精读后端 action 路由中心。它支持的 action 包括：

- `search_paper`
- `upload_paper`
- `get_paper_detail`
- `start_reading`
- `pause_reading`
- `resume_reading`
- `get_session_state`
- `get_progress`
- `load_skill`
- `unload_skill`
- `fork`
- `merge`
- `kg_query`

### 2.2 导入 PDF 的数据流

本地 PDF：

```text
用户选择文件
  -> app.js importLocalPdf()
  -> FileReader 读成 base64
  -> POST /paper_reading { action: "upload_paper", pdf_data, metadata }
  -> handler._handle_upload_paper()
  -> PaperPipeline.parse_pdf_bytes()
  -> PDFParser.parse_bytes()
  -> PaperMetadata
  -> storage.save_paper()
  -> storage.save_upload()
  -> kg_builder.build_full_paper()
  -> storage.save_kg()
  -> 返回 paper_id、sections 摘要、figures_count、kg_build
  -> 前端 acceptUploadedPaper()
  -> 再调用 get_paper_detail()
```

URL/arXiv PDF：

```text
用户输入 URL/arXiv
  -> app.js normalizePdfUrl()
  -> POST /paper_reading { action: "upload_paper", pdf_url }
  -> 后端 httpx 下载 PDF
  -> 后续解析链路同本地 PDF
```

### 2.3 加载论文详情的数据流

```text
前端 loadPaperDetail()
  -> POST /paper_reading { action: "get_paper_detail", paper_id }
  -> storage.load_paper()
  -> 必要时 PDFParser.sections_need_repair() + extract_sections() 做旧数据修复
  -> _paper_detail_for_response()
  -> 返回 paper、pdf_url、has_pdf、initial_kg
  -> 前端渲染结构化正文、PDF iframe、初始 KG
```

`get_paper_detail` 返回的 `paper` 是前端重排展示的关键数据，里面包含：

- `sections[]`：`section_id`、`title`、`level`、`content`、`paragraphs`、`start_page`、`end_page`
- `figures[]`：`figure_id`、`caption`、`page`、`section_id`、`image_url` 等
- `tables[]`：当前基本是透传字段，PDFParser 目前没有真正结构化抽表
- `references[]`
- `full_text`

### 2.4 开始/继续精读的数据流

```text
前端 startReading(content)
  -> POST /paper_reading {
       action: "start_reading",
       session_id,
       paper_id,
       target_section: state.currentSection,
       content,
       metadata: { viewport_section, selected_text }
     }
  -> handler._handle_start_reading()
  -> 获取/创建 ReadingSession
  -> 加载 paper_data
  -> ensure_full_paper_kg()
  -> get_revealed_subgraph(current_section)
  -> _build_start_reading_context()
  -> run_agent_detailed()
  -> postprocess_agent_output()
  -> session_mgr.update_progress(completed=True)
  -> 返回 agent_response、session、progress、revealed_kg、skill_outputs
  -> 前端 applyReadingPayload()
```

前端“把信息返回给后端”的方式主要有三类：

- 普通问题/按钮指令放在 `content` 字段中。
- 当前章节放在 `target_section` 字段中。
- 选中文本有两种传法：
  - 对“解释”和“概念脉络”这类操作，前端会把选中文本拼进 `content`，因此后端和 LLM 能看到。
  - 对 Fork，前端会把选中文本放入 `fork_context`。
  - 前端也会在 `metadata.selected_text` 放一份，但当前后端 `_handle_start_reading()` 并没有使用 metadata 里的 selected_text；真正起作用的是拼进 `content` 或 `fork_context` 的文本。

### 2.5 目前已实现的论文精读功能

已实现的功能包括：

- 论文搜索：arXiv / Semantic Scholar / all，经 `PaperPipeline.search()`。
- PDF 导入：本地 base64 和 URL 下载两种。
- PDF 解析：基于 PyMuPDF 抽取全文、章节、摘要、标题、作者、参考文献、图像裁剪。
- 论文重排：前端按 sections/paragraphs 重排展示，并插入 figure 图片。
- PDF 原文查看：iframe 加载后端保存的原始 PDF。
- 章节导航：目录点击、上一节/下一节、滚动定位当前 section。
- Session 管理：创建、恢复、暂停、checkpoint、进度保存。
- 阅读进度：按章节完成数计算百分比。
- Agent 精读：把论文元信息、当前章节、目录、进度、已展开 KG 注入 prompt 后调用 LLM agent。
- Skill 开关：加载/卸载 8 个 reading skill。
- Skill 快捷运行：先 load skill，再用该 skill 的 prompt 调 start_reading。
- 选中文本工具条：解释、公式推导、概念脉络、Fork 深入、KG 候选。
- Fork/Merge：创建子会话、在右侧生成独立 tab、可合并回主流程。
- 知识图谱：上传/首次阅读时构建完整 KG，阅读时渐进展示。
- KG 查询：search/path/neighbors/subgraph 四类入口，返回自然语言答案、证据、推理路径和图元素。

需要注意的半成品或限制：

- “KG 候选”按钮目前只是 toast 提示，后端没有确认写入 KG 的 action。
- `tables` 字段存在，但 PDFParser 当前没有真正结构化抽表。
- PDF 原文里没有实现选中文本捕获和坐标映射。
- 公式只是被当作文本段落识别并加 CSS class，不是 LaTeX/MathML 级别的结构化公式。

### 2.6 涉及的 LLM agent 技术

论文精读模块涉及以下 agent/LLM 技术：

- Agent profile：`agents/profiles.json` 定义 `paper_reading_agent` 的角色、工具、默认 skill 和候选 skills。
- Tool calling：`runtime/agent_runner.py` 把 agent profile 中允许的工具转成 OpenAI tools，支持多步工具调用，最多 `max_steps=5`。
- 工具注册表：`tools/registry.py` 注册 `paper_search`、`pdf_parse`、`kg_query`、`kg_build` 等工具。
- Skill prompt injection：`run_agent_detailed()` 会通过 `resolve_runtime_capabilities()` 把默认 skill 和可能选择出的专项 skill 合并进 system prompt。
- Capability selector：`CapabilitySelector` 会调用 LLM，从候选 skills 中选择至多一个专项 skill。
- KG LLM 抽取：`ProgressiveKGBuilder._extract_full_paper_kg_with_llm()` 调 LLM，要求返回 JSON `{nodes, edges}`。
- KG 驱动问答：`KGQueryEngine._compose_answer()` 在有模型时会把 matched nodes、reasoning paths、evidence 交给 LLM 生成答案。
- 结构化输出后处理：`postprocess_agent_output()` 对 LLM 文本尝试抽 JSON，再包装成前端 `skill_outputs`。
- Fork/Merge：通过子 session 隔离专项分析上下文，再合并 key findings 和 active skills。

## 3. 论文重排在哪里实现、如何实现、当前问题原因分析

### 3.1 实现位置

论文重排不是前端直接解析 PDF，而是后端解析出结构化 sections，前端负责渲染。

后端解析位置：

- `handlers/paper_reading/pipeline/parser.py`
  - `PDFParser.parse()`
  - `PDFParser.parse_bytes()`
  - `PDFParser._parse_document()`
  - `PDFParser._extract_page_text()`
  - `PDFParser._extract_figures()`
  - `PDFParser.extract_sections()`

前端展示位置：

- `gateway/static/paper-reading/app.js`
  - `renderSections()`
  - `renderReflowParagraph()`
  - `renderPaperFigure()`
  - `renderPdf()`

### 3.2 当前重排实现方式

后端 `PDFParser._parse_document()` 的主流程是：

1. 用 PyMuPDF 打开 PDF。
2. 先 `_extract_figures()`：通过 Figure/Fig caption 正则定位 caption，再裁剪 caption 上方的图像/矢量区域，生成 PNG。
3. 把 figure 的 bbox 作为 excluded regions。
4. 对每页调用 `_extract_page_text()`：
   - 遍历 `page.get_text("dict")["blocks"]`
   - 只处理文字 block
   - 跳过落在 figure 区域里的 block
   - 跳过 Figure caption
   - 按 block 内 line/spans 拼接文本
5. 全文拼成 `full_text`。
6. `extract_sections(full_text)` 用正则和启发式识别 Abstract、References、编号标题和 appendix。
7. `_assign_section_pages()` 根据标题在 page_texts 中出现的位置估算 section 起止页。
8. `_assign_figure_sections()` 根据页码、caption 词、正文引用把 figure 归属到 section。
9. 返回 `PaperMetadata`。

前端 `renderSections()` 的展示逻辑：

1. 遍历 `state.paper.sections`。
2. 每个 section 渲染成 `section.paper-section`。
3. 段落优先用 `section.paragraphs`，否则用 `splitParagraphs(section.content)`。
4. 根据 figure 的 `section_id` 或 page 范围，把图插入到段落之间。
5. `renderReflowParagraph()` 用非常轻量的启发式给公式/项目符号/lead phrase 添加 CSS class。

### 3.3 当前公式、图表、注释错位的原因

你提到的问题是合理的，根因主要在后端解析阶段，而不是前端展示阶段。

问题 1：识别错位。

- `_extract_page_text()` 依赖 PyMuPDF 的 block 顺序，没有显式做双栏/多栏阅读顺序重建。
- 对双栏论文，PDF block 的自然顺序可能是左栏一块、右栏一块、页眉/页脚/浮动图交错，导致重排正文错位。
- section 起止页是通过标题字符串在 page_texts 里粗略查找，不是通过 PDF 坐标和真实结构树定位，figure 插入位置也只是按段落索引估算。

问题 2：公式不能以原格式展示。

- 当前没有公式抽取模型，也没有 LaTeX/MathML 识别。
- 公式只是在 `_extract_page_text()` 中被当作普通 text span 拼成行，再由 `_lines_to_paragraphs()` 合并成段落。
- 前端 `renderReflowParagraph()` 只根据长度和是否含有 `=` 等符号加 `is-equation` 样式；这只是视觉样式，不保留公式二维排版、上下标、分式、矩阵、编号对齐。
- PDF 中很多公式是 glyph/矢量/特殊字体组合，单靠文本抽取很容易丢失空间关系。

问题 3：图表部分无法正确展示原论文格式。

- 图像提取目前只针对 Figure/Fig caption，靠 caption 上方区域裁剪，适合常规“图在 caption 上方”的论文，但对跨栏图、caption 在侧边/上方、子图分散、表格、算法框、复杂矢量图都不稳。
- `PaperTable` 模型存在，但 PDFParser 当前返回 `tables=[]`，没有表格结构识别。
- 前端只能展示 `figures[].image_url`，并没有表格 HTML 重建、单元格解析、公式表格混排。

问题 4：注释被识别成 section。

- `extract_sections()` 的标题识别规则核心是编号标题，例如 `1 Introduction`、`4.1 Coarse-grained Memory Retrieval`，并用 `_looks_like_heading_title()` 判断下一行是否像标题。
- 如果脚注/注释/图注/边注出现“数字行 + 短英文标题样式行”，或参考文献/公式编号附近文本满足标题启发式，就可能被误切成 section。
- 当前已有一些防护：检查顶层编号连续性、排除含 `=`、`%`、括号等符号的标题、限制标题长度和词数、排除页码。但这些仍然是启发式，不能覆盖所有 PDF 布局。

### 3.4 重排问题的改进方向

如果要修正当前重排质量，建议优先从后端解析层做：

- 增加版面分析：按页检测单栏/双栏，按列、y 坐标、x 坐标重排 block，而不是直接使用 PyMuPDF block 顺序。
- 让 section 识别基于字体大小、粗体、坐标、编号连续性、目录线索，而不是只看纯文本正则。
- 把 footnote、caption、header/footer、page number 做区域级过滤。
- 对公式建立独立 `PaperFormula` 模型，至少保留 bbox、page、raw text、image crop；展示时用公式截图兜底。
- 对表格建立独立 `PaperTable` 抽取逻辑，初期可先用 page crop + caption 展示，再考虑结构化单元格。
- figure/table/formula 与 section 的关联应优先使用 bbox 和 section span，而不是仅按页码和段落估算。

## 4. 标亮一段内容后加载 skill 分析是否只能在论文重排界面进行

按当前代码实现：是的，可靠地说只能在“论文重排”界面进行。

原因在 `app.js`：

- 选中文本监听绑定在 `structured-reader` 上：`structured-reader.addEventListener("mouseup", captureSelection)`。
- `captureSelection()` 会检查 selection 的 anchor 是否在 `#structured-reader` 内：`anchor.closest("#structured-reader")`。
- PDF 原文模式是 iframe：`<iframe id="pdf-frame">`。代码没有进入 iframe 获取 selection，也没有 PDF.js text layer 或坐标映射。
- 页面里也有 PDF 模式提示：选中解释/公式推导/概念脉络/KG 候选需要切回“论文重排”视图。

因此：

- 在重排界面选中段落：可以弹出工具条，可以解释、概念分析、Fork 公式分析。
- 在 PDF 原文 iframe 里选中：当前主页面拿不到 iframe 内 selection，也不会触发 `captureSelection()`。

如果希望 PDF 原文也支持高亮分析，需要改成 PDF.js 自渲染或对 iframe 做同源 selection 抽取，并建立“PDF 坐标/页码 -> section/paragraph -> 后端上下文”的映射。当前实现没有这条链路。

## 5. 前端左边栏阅读进度如何标定

阅读进度的最终标定来自后端 session progress，不是前端滚动百分比。

后端位置：

- `handlers/paper_reading/harness/session.py`
  - `SessionManager.update_progress()`
  - `SessionManager.set_total_sections()`

后端逻辑：

- `start_reading` 时，如果加载到 paper_data，就调用 `set_total_sections(session_id, len(sections))`。
- 每次 `_handle_start_reading()` 完成 agent 分析后调用：

```text
session_mgr.update_progress(
    session.session_id,
    section_id=current_section or "abstract",
    paragraph_index=0,
    completed=True,
)
```

- `completed=True` 会把当前 section 加入 `progress.completed_sections`。
- `percentage = len(completed_sections) / total_sections * 100`。
- `section_statuses[section_id] = "completed"`。
- `current_position = { section_id, paragraph_index }`。

前端位置：

- `renderProgress()`：读取 `state.progress.total_sections`、`completed_sections`、`percentage`，更新左栏百分比、进度条宽度和说明。
- `renderOutline()`：读取 `state.progress.section_statuses`，已完成章节显示完成图标，否则显示序号。
- `updateCurrentSectionFromScroll()`：只根据结构化阅读区滚动更新 `state.currentSection`，用于定位和 composer context；它不会把章节标成 completed。

因此当前阅读进度的语义是“有多少章节触发并完成过一次 start_reading 分析”，不是“用户实际滚动阅读了多少正文”。

## 6. 论文知识图谱最后构建成什么样、前端如何展示

### 6.1 后端最终数据结构

知识图谱后端核心是 `KnowledgeGraphEngine`，内部使用 `networkx.DiGraph`。每个节点和边都带完整属性。

节点类型共 13 种：

- `Problem`
- `Method`
- `Module`
- `Baseline`
- `Metric`
- `Dataset`
- `Experiment`
- `Figure`
- `Concept`
- `Limitation`
- `Claim`
- `RelatedWork`
- `Insight`

边类型共 9 种：

- `motivates`
- `extends`
- `outperforms`
- `depends_on`
- `contradicts`
- `ablates`
- `inspired_by`
- `evaluated_on`
- `contributes_to`

节点主要字段：

- `node_id`
- `node_type`
- `label`
- `paper_id`
- `section_id`
- `properties`
- `confidence`
- `created_at`

边主要字段：

- `edge_id`
- `source_id`
- `target_id`
- `edge_type`
- `label`
- `paper_id`
- `properties`
- `confidence`
- `created_at`

`properties.read_stage` 是前端渐进展示的关键字段，取值为：

```text
abstract / introduction / method / experiment / conclusion / general
```

### 6.2 构建方式

现在的主路径是“整篇一次性构建 + 阅读时渐进展示”。

上传或首次阅读时：

```text
kg_builder.build_full_paper(paper_id, paper_data, model)
```

构建流程：

1. 如果已有该 paper 的节点，默认不重建。
2. 优先调用 LLM：`_extract_full_paper_kg_with_llm()`。
3. LLM prompt 要求输出 JSON：`{"nodes": [...], "edges": [...]}`。
4. 如果 LLM 没有抽出节点，走 `_extract_full_paper_kg_heuristic()` 兜底。
5. `_materialize_nodes()` 把 raw nodes 转成 Pydantic KGNode 子类，去重并补 `node_id`。
6. `_materialize_edges()` 把 raw edges 转成 KGEdge 子类，只保留合法类型和合法 source/target。
7. 写入 `KnowledgeGraphEngine` 的 NetworkX DiGraph。
8. `storage.save_kg()` 持久化成 JSON-like dict。

启发式兜底会至少创建：

- 主问题 `Problem`
- 主方法 `Method`
- `Problem -> Method` 的 `motivates` 边
- 方法章节中的 `Module`
- 摘要关键词形成的 `Concept`
- references 中的 `RelatedWork`
- 实验章节里的 `Dataset`/`Experiment`
- 结论里的 `Claim`

### 6.3 渐进展示方式

阅读某一章节时：

```text
kg_builder.get_revealed_subgraph(paper_id, current_section)
```

它会：

1. 用 `classify_section(current_section)` 判断当前阅读阶段。
2. 根据阶段顺序允许展示不晚于当前阶段的节点：

```text
abstract -> introduction -> method -> experiment -> conclusion -> general
```

3. 只返回 `properties.read_stage` 在 allowed stages 中的 nodes。
4. 只返回 source/target 都已展示且 edge read_stage 也允许的 edges。
5. 输出：

```text
{
  paper_id,
  current_stage,
  allowed_stages,
  nodes,
  edges,
  node_count,
  edge_count,
  cytoscape_elements
}
```

这里的 `cytoscape_elements` 是 Cytoscape 风格的数据结构：

```text
节点: { data: { id, label, node_type, paper_id, section_id, properties, color } }
边:   { data: { id, source, target, edge_type, label, properties } }
```

### 6.4 前端展示样子

虽然字段叫 `cytoscape_elements`，当前前端并没有引入 Cytoscape.js，而是在 `app.js` 的 `renderKg(elements)` 中手写 SVG 展示。

前端 KG 展示特征：

- 底部 `kg-panel` 中一个 SVG：`<svg id="kg-graph" viewBox="0 0 900 360">`。
- 节点以圆形展示，颜色来自 `NODE_COLORS`。
- 节点标签展示在圆下方，会截断。
- 边用 SVG line + arrow marker 展示，边标签显示在连线中点附近。
- 支持 4 种布局：
  - `force`：手写力导向模拟，可拖动节点。
  - `circle`
  - `grid`
  - `grouped`
- 点击节点会更新右侧 inspector，展示 node_type、label、summary/properties，并可跳到对应正文 section 或查邻域。
- KG 查询结果会替换/叠加为 query subgraph，同时右侧展示自然语言 answer、reasoning_paths、evidence cards。

前端还有一个“只增不减”的展示策略：

- `applyReadingPayload()` 用 `mergeKgElements(existing, incoming)` 合并新阶段图元素。
- `kgMaxStageIndex` 记录已展开到的最远阶段。
- 因此用户读到后面章节后，即使回到前面章节，前端已展示图谱不会自动收缩。

## 7. Skill 加载过程、代码如何使用 skill、返回输出如何组织并展示

### 7.1 Skill 文件组织

内置 reading skills 在：

```text
skills/builtin/reading/
```

共有 8 个：

- `reading.method_analyst`
- `reading.critique_agent`
- `reading.math_verifier`
- `reading.code_reviewer`
- `reading.domain_expert`
- `reading.writing_coach`
- `reading.idea_generator`
- `reading.cross_paper_linker`

每个目录下有一个 `SKILL.md`，文件结构是：

```text
---
id: ...
name: ...
category: reading
description: ...
when_to_use:
...
---

Markdown 指令正文
```

### 7.2 后端 SkillRegistry 如何加载

启动时：

```text
create_skill_registry()
  -> SkillRegistry()
  -> scan()
  -> _scan_builtin_skills()
  -> _scan_user_skills()
```

`SkillRegistry` 做两件事：

1. 启动时只读取 metadata，建立 `skill_id -> SkillRecord(path, summary)` 索引。
2. 真正执行 agent 时，第一次需要某个 skill 才调用 `get_instructions(skill_id)` 懒加载完整 `SKILL.md` 正文，并缓存在 `_instructions`。

metadata 解析由 `skills/loader.py` 完成：

- `_read_skill_parts()` 读取 YAML Front Matter 和 Markdown 正文。
- `load_skill_metadata()` 只读元数据。
- `load_skill_document()` 读取完整 instructions。
- Pydantic 模型在 `skills/models.py` 中校验 id/name/category/description/instructions。

### 7.3 Agent 如何使用 skill

`paper_reading_agent` 在 `agents/profiles.json` 中声明：

- `default_skill`: `reading.method_analyst`
- `skills`: 8 个 reading skill
- `tools`: `paper_search`、`pdf_parse`、`kg_query`、`kg_build`

执行 `start_reading` 时：

```text
handler._handle_start_reading()
  -> run_agent_detailed(
       agent=paper_agent,
       user_content=content_msg,
       tool_registry,
       skill_registry,
       capability_selector,
       max_steps=5
     )
```

`run_agent_detailed()` 内部：

1. `resolve_runtime_capabilities()` 读取 agent profile。
2. 从 `skill_registry` 加载默认 skill 指令。
3. 把候选 skill summaries 交给 `CapabilitySelector.select()`。
4. selector 用 LLM 选择至多一个专项 skill。
5. 如果选择成功，再加载该 skill 指令。
6. `build_system_prompt()` 把 agent role、default skill、selected skill 拼成 system prompt。
7. 调用模型；如果模型发起 tool calls，就检查工具是否在 agent profile 允许列表内，再执行工具，把结果作为 tool message 继续喂给模型。
8. 返回 `AgentRunResult(text, duration_ms, usage, model_calls)`。

这里有一个容易混淆的点：

- 前端 `load_skill/unload_skill` 修改的是 session 的 `active_skills`。
- `run_agent_detailed()` 的 skill prompt 注入主要来自 agent profile 的 default skill + selector 自动选择。
- session active skills 主要用于：
  - 写入 `_build_start_reading_context()` 的上下文，让 LLM 知道当前 active skills。
  - 决定 `postprocess_agent_output()` 要按哪些 skill 包装输出。

也就是说，“手动 load skill”不等于直接强制把该 skill 的 `SKILL.md` 注入 system prompt；它更明确地影响 session 状态、用户上下文和后处理输出。前端快捷运行 `runSkill(skill)` 会先 load skill，然后把该 skill 对应 prompt 放进 `content`，这样 LLM 实际上会收到专项任务指令。

### 7.4 Skill 输出如何组织

Agent 原始输出是 `result.text`。随后 handler 会决定 active skill ids：

```text
_active_skill_ids_for_context(session.active_skills, current_section)
```

规则：

- 如果 session.active_skills 非空，用它。
- 如果当前章节像 experiment/result，默认 `reading.critique_agent`。
- 如果当前章节像 conclusion，默认 `reading.idea_generator`。
- 其他情况默认 `reading.method_analyst`。

然后：

```text
postprocess_agent_output(
    result.text,
    skill_ids=active_skill_ids,
    paper_id=paper_id,
    section_id=current_section,
    trigger="fork" if fork session else "auto"
)
```

每个 postprocessor 做类似操作：

1. 尝试从 LLM 文本中抽取 JSON object。
2. 如果成功，放到 `content`。
3. 生成 Markdown 版 `rendered`。
4. 生成可能的 `kg_candidates`。
5. 返回前端可消费的 dict：

```text
{
  skill_id,
  skill_name,
  trigger,
  output_type,
  content,
  rendered,
  kg_candidates,
  parse_status
}
```

例如：

- `method_analyst` 会把 `pipeline[]` 转为 Module 类型 KG 候选。
- `math_verifier` 会把 `formula` 转为 Concept 类型 KG 候选。
- `critique_agent` 可能产生 Limitation 候选。

但是注意：这些 `kg_candidates` 当前只是返回给前端展示，尚未看到“确认写入 KG”的后端 action。

### 7.5 前端如何展示 Skill 输出

前端 `applyReadingPayload()` 收到 `payload.skill_outputs` 后：

```text
state.skillOutputs = payload.skill_outputs || []
renderSkillOutputs(state.skillOutputs, analysis-feed)
```

`renderSkillOutputs()` 会为每个 skill output 生成一张 `skill-output-card`：

- header 显示 `skill_name` 和 `output_type/parse_status`。
- 如果 `parse_status === "parsed"` 且 `content` 是结构化对象，则用 `renderSkillContent()` 展示。
- `math_derivation` 特殊走 `renderMathTabs()`，按直觉理解、逐步推导、数值例子、推导跳跃分 tab。
- 其他结构化内容走 `renderStructuredValue()`。
- 如果没有结构化结果，则展示 `output.rendered` markdown。
- 如果有 `kg_candidates`，显示候选数量徽标。

Skill 开关展示在左侧 `skill-switches`：

- `toggleSkill()` 调 `load_skill/unload_skill`。
- 成功后更新 `state.activeSkills`。
- `syncSkillControls()` 同步 checkbox 和 active skill 数量。

快捷按钮展示在右侧 quick actions：

- `runSkill(skill)` 如果 session 不存在会先初始化阅读。
- 如果 skill 未激活，会先调用 `load_skill`。
- 然后把该 skill 的 prompt 作为 `content` 调 `startReading()`。

## 8. Agent 加载 Skill 与调用工具的完整代码链路

本节专门把当前论文精读 agent、skill、tool 的完整链路按代码重新理清。相关代码主要分布在：

- `gateway/app.py`：启动时创建 agent、tool registry、skill registry、selector，并注入 `app.state`。
- `agents/agent.py`、`agents/profiles.json`：定义 agent profile、默认 skill、候选 skill、可用工具白名单。
- `runtime/agent_runner.py`：真正执行 agent、加载 skill、选择 skill、暴露工具、处理 tool calls。
- `skills/registry.py`、`skills/loader.py`、`skills/selector.py`：扫描 skill、懒加载 skill 正文、用 LLM 选择专项 skill。
- `tools/base.py`、`tools/registry.py`、`tools/builtin/*.py`：工具协议、工具注册、工具 schema、工具执行。
- `handlers/paper_reading/handler.py`：论文精读业务层，负责构造上下文、调用 agent、处理 skill output、更新 session。
- `handlers/paper_reading/postprocessors/postprocess.py`：按 skill id 路由后处理器，把 agent 输出包装成前端卡片。

### 8.1 总体调用时序

从用户点击“分析本节”或在右侧输入问题开始，完整链路是：

```text
前端 startReading()
  -> POST /paper_reading { action: "start_reading", paper_id, session_id, target_section, content }
  -> WebChannel.receive_message()
  -> process_channel_input()
  -> handle_paper_reading_message()
  -> _handle_start_reading()
  -> _build_start_reading_context()
  -> run_agent_detailed()
       -> resolve_runtime_capabilities()
            -> SkillRegistry.get_instructions(default_skill)
            -> SkillRegistry.list_summaries(candidate skills)
            -> CapabilitySelector.select()
            -> SkillRegistry.get_instructions(selected_skill)
            -> build_system_prompt()
       -> ToolRegistry.to_openai_tools(agent.profile.tools)
       -> model.chat(messages, tools, tool_choice="auto")
       -> 如果模型返回 tool_calls:
            -> run_tool_call()
            -> tool_registry.get(tool_name)
            -> tool.run(arguments)
            -> 把工具结果作为 role="tool" message 追加回 messages
            -> 再次 model.chat()
       -> 返回 AgentRunResult
  -> _active_skill_ids_for_context()
  -> postprocess_agent_output()
  -> SessionManager.update_progress()
  -> 返回 agent_response + skill_outputs + progress + KG
  -> 前端 appendAnalysis() + renderSkillOutputs()
```

这条链路里有三种“路由”：

- action 路由：`handlers/paper_reading/handler.py` 的 `handler_map` 把 `start_reading/load_skill/kg_query` 等 action 分发到不同函数。
- skill 路由：`SkillRegistry` 负责根据 skill id 找 `SKILL.md`；`CapabilitySelector` 负责运行时选择是否附加专项 skill；`POSTPROCESSORS` 负责根据 skill id 找 Python 后处理器。
- tool 路由：`ToolRegistry` 根据工具名找到具体 `BaseTool` 实例；`run_tool_call()` 根据模型返回的 tool call name 执行工具。

### 8.2 启动期：agent、skill、tool 如何被创建并注入

启动入口是 `gateway/app.py` 的 `start_gateway_server()`。关键代码位置：

- `gateway/app.py:173` 定义启动函数。
- `gateway/app.py:176-178` 创建 `chat_agent`、`domain_onboarding_agent`、`paper_reading_agent`。
- `gateway/app.py:189-190` 把 KG engine/builder 注入给 KG 工具。
- `gateway/app.py:193-195` 创建 `tool_registry`、`skill_registry`、`capability_selector`。
- `gateway/app.py:201` 把 `paper_reading_agent` 存到 `app.state`。
- `gateway/app.py:207-209` 把 tool/skill/selector 存到 `app.state`。

对应逻辑可以理解为：

```text
model = OpenAIClient(...)
paper_reading_agent = create_agent(model, "paper_reading")
tool_registry = create_builtin_tool_registry()
skill_registry = create_skill_registry()
capability_selector = CapabilitySelector()

app.state.paper_reading_agent = paper_reading_agent
app.state.tool_registry = tool_registry
app.state.skill_registry = skill_registry
app.state.capability_selector = capability_selector
```

为什么这样设计：

- `app.state` 是 FastAPI 进程内共享依赖容器，避免每个请求重复创建 agent、registry、KG engine。
- agent、tool、skill 都在启动期准备好，请求期只做选择和执行。
- KG 工具需要访问同一个 `KnowledgeGraphEngine`，所以 `set_kg_engine()` 和 `set_kg_builder()` 在启动期做依赖注入。

### 8.3 Agent profile 如何决定默认 Skill、候选 Skill 和工具白名单

`agents/agent.py` 里 `Agent` 会读取 `agents/profiles.json` 中对应 type 的 profile。关键代码：

- `agents/agent.py` 的 `AgentProfile` 包含 `name/type/role/system_prompt/tools/default_skill/skills`。
- `create_agent(model, "paper_reading")` 会构造 `Agent(agent_type="paper_reading", llm=model)`。

`agents/profiles.json` 中 `paper_reading_agent` 的关键字段是：

```text
type: "paper_reading"
role: "paper_reading"
tools:
  - paper_search
  - pdf_parse
  - kg_query
  - kg_build
default_skill: reading.method_analyst
skills:
  - reading.method_analyst
  - reading.critique_agent
  - reading.math_verifier
  - reading.code_reviewer
  - reading.domain_expert
  - reading.writing_coach
  - reading.idea_generator
  - reading.cross_paper_linker
```

这里有两个重要设计：

1. 工具白名单在 agent profile 上，而不是让模型访问全部 registry。

   `ToolRegistry` 里注册了 `get_current_time`、`paper_search`、`pdf_parse`、`kg_query`、`kg_build`，但论文精读 agent 的 `tools` 只包含后四个。所以即使 registry 有时间工具，论文精读 agent 也不会把它暴露给模型。

2. Skill 分成默认 skill 和候选 skill。

   `reading.method_analyst` 是默认 skill，总是优先加载。其他 reading skill 作为候选，由 selector 根据当前任务选择是否额外加载一个。

为什么这样设计：

- 白名单限制工具调用边界，避免模型调用不相关工具。
- 默认 skill 保证 agent 有稳定的基础行为。
- 候选 skill 让同一个 agent 可以临时变成公式验证、审稿、复现审查、写作教练等专家，而不需要为每个专家新建一个完整 agent。

### 8.4 SkillRegistry 如何扫描与懒加载 Skill

Skill 扫描在 `skills/registry.py`：

- `skills/registry.py:25` 定义 `SkillRegistry`。
- `skills/registry.py:39` 的 `scan()` 清空索引后扫描 builtin 和 user skill。
- `skills/registry.py:46` 的 `_scan_builtin_skills()` 扫描 `skills/builtin/domain|reading|chat|custom/**/SKILL.md`。
- `skills/registry.py:74` 的 `_scan_user_skills()` 扫描用户目录 `~/.novicesynapse/skills`。
- `skills/registry.py:85` 的 `_register()` 读取 metadata、校验 category、检查重复 id，并记录 `skill_id -> SkillRecord(summary, path)`。

Skill 文件解析在 `skills/loader.py`：

- `skills/loader.py:54` 的 `load_skill_metadata()` 只读取 YAML Front Matter。
- `skills/loader.py:60` 的 `load_skill_document()` 读取 Front Matter 和 Markdown 正文。

运行期加载正文在：

- `skills/registry.py:115` 的 `get_instructions(skill_id)`。

这一步有缓存：

```text
if skill_id in self._instructions:
    return self._instructions[skill_id]
...
document = load_skill_document(record.path, record.summary.source)
self._instructions[skill_id] = document.instructions
```

为什么这样设计：

- 启动时只读 metadata，速度快，能建立候选列表。
- 真正需要某个 skill 时才读 Markdown 正文，减少无关 prompt 常驻内存和启动开销。
- Skill 正文缓存后，同一进程后续请求不用重复读文件。
- 内置 skill 和用户 skill 共用同一个 registry，但 source 不同，便于未来扩展用户自定义 skill。

### 8.5 Runtime 如何把 Skill 注入 Agent Prompt

核心在 `runtime/agent_runner.py`。

`run_agent_detailed()` 在 `runtime/agent_runner.py:278` 定义。它开始执行时先调用：

```text
system_prompt = resolve_runtime_capabilities(
    agent=agent,
    user_content=user_content,
    skill_registry=skill_registry,
    capability_selector=capability_selector,
)
```

`resolve_runtime_capabilities()` 在 `runtime/agent_runner.py:198`。它做四步：

1. 从 `agent.profile` 读取：
   - `default_skill_id`
   - `registered_skills`
   - `profile.system_prompt`

2. 加载默认 skill：

```text
default_skill = skill_registry.get_instructions(default_skill_id)
```

3. 列出候选 skill summaries，并排除默认 skill：

```text
skill_registry.list_summaries(registered_skills)
```

4. 调用 `CapabilitySelector.select()` 让 LLM 从候选 skill 中选择至多一个：

```text
selection = capability_selector.select(
    model=agent.llm,
    role=profile.role,
    user_task=user_content,
    skill_summaries=skill_summaries,
)
```

`CapabilitySelector` 在 `skills/selector.py:74`，核心 prompt 要求模型：

```text
Select at most one optional Skill needed for the current task.
Return one JSON object with skill and reason.
skill must be a candidate Skill id or null.
```

selector 返回后，`runtime/agent_runner.py:254` 用 `validate_capability_selection()` 校验模型选择的 skill 必须在候选白名单里，防止模型编造或越权选择。

如果选择了某个 skill，就再：

```text
selected_skill = skill_registry.get_instructions(selection.skill)
```

最后由 `build_system_prompt()` 拼装：

```text
[Agent Role]

{profile.system_prompt}

{default_skill instructions}

{selected_skill instructions}
```

为什么这样设计：

- 让 agent role、默认阅读策略、专项 skill 指令处在 system prompt 层，优先级高于用户输入。
- selector 只允许选择一个专项 skill，避免一次性塞入 8 个大 prompt 导致上下文膨胀和指令冲突。
- selector 输出再经过白名单校验，避免“模型自己发明 skill id”。
- 如果 selector 失败，代码会 fallback 到 default skill，保证主流程不被 skill 选择失败阻断。

### 8.6 前端手动 load_skill 和运行时 Skill 注入不是同一件事

这是当前实现最容易误解的地方。

前端左侧 Skill 开关调用：

```text
POST /paper_reading { action: "load_skill", session_id, skill_ids: [...] }
```

后端路由到：

- `handlers/paper_reading/handler.py:427` 的 `_handle_load_skill()`
- `handlers/paper_reading/handler.py:443` 的 `_handle_unload_skill()`

它们只调用 `SessionManager.activate_skills()` / `deactivate_skills()`，修改的是：

```text
session.active_skills
```

这会影响三件事：

1. `_build_start_reading_context()` 会把 `session.active_skills` 写入给 LLM 的 user context。
2. `_active_skill_ids_for_context()` 会优先用 `session.active_skills` 决定后处理器列表。
3. 前端 `syncSkillControls()` 会把开关显示为已激活。

但它不直接调用 `skill_registry.get_instructions(skill_id)`，也不直接强制把这个 skill 的 `SKILL.md` 注入 system prompt。真正的 system prompt 注入仍发生在 `run_agent_detailed() -> resolve_runtime_capabilities()`，由 agent profile 的默认 skill 和 selector 决定。

前端快捷运行 `runSkill(skill)` 为什么更像“强制使用某个 skill”：

- 它先调用 `load_skill`，让 session active skills 包含该 skill。
- 然后把该 skill 对应的 prompt 文案作为 `content` 发给 `start_reading()`。
- 这样 LLM 至少会在用户任务里明确收到“请做公式验证/领域定位/审稿”等指令。
- 后处理也会按 active skill 生成对应 `skill_outputs`。

所以当前实现里：

- `load_skill` 是 session 状态和后处理路由的开关。
- `CapabilitySelector` 是 system prompt 层专项 skill 的自动路由。
- `runSkill(skill.prompt)` 是前端层面触发专项分析的直接方式。

这种设计的好处是实现简单、主流程稳定；代价是“用户手动激活 skill”与“系统 prompt 强制注入该 skill”之间还没有完全等价。

### 8.7 Skill 路由具体有三层

第一层：文件加载路由。

`SkillRegistry._records` 保存：

```text
skill_id -> SkillRecord(summary, path)
```

当运行期需要 `reading.math_verifier` 时：

```text
SkillRegistry.get_instructions("reading.math_verifier")
  -> 找到对应 SKILL.md path
  -> load_skill_document()
  -> 返回 Markdown instructions
```

第二层：运行时选择路由。

`CapabilitySelector.select()` 根据当前 `user_content` 和候选 skill summaries 返回：

```text
{ "skill": "reading.math_verifier", "reason": "..." }
```

或：

```text
{ "skill": null, "reason": "..." }
```

这个选择只影响本次 agent 的 system prompt。

第三层：输出后处理路由。

`handlers/paper_reading/postprocessors/postprocess.py` 中：

```text
POSTPROCESSORS = {
    "reading.method_analyst": method_analyst.postprocess,
    "reading.critique_agent": critique_agent.postprocess,
    "reading.math_verifier": math_verifier.postprocess,
    ...
}
```

`postprocess_agent_output()` 遍历 `skill_ids`，找到对应 processor，生成前端 `skill_outputs`。

为什么后处理也要按 skill id 路由：

- 不同 skill 期望的结构化 JSON 不同。
- `math_verifier` 需要渲染三层公式推导 tab。
- `method_analyst` 需要提取 pipeline 并生成 Module KG 候选。
- `critique_agent`/`idea_generator` 等则需要生成审稿/想法类结构化卡片。

### 8.8 工具如何注册、选择、暴露给模型

工具基础协议在 `tools/base.py`：

- `ToolSpec` 包含 `name`、`description`、`parameters`。
- `BaseTool` 要求每个工具有 `spec` 和 `run(arguments)`。

工具注册在 `tools/registry.py`：

- `tools/registry.py:14` 定义 `ToolRegistry`。
- `tools/registry.py:20` 的 `register()` 按 `tool.name` 存工具实例。
- `tools/registry.py:24` 的 `get()` 按 name 取工具。
- `tools/registry.py:36` 的 `to_openai_tools()` 把工具转成 OpenAI function tool schema。
- `tools/registry.py:51` 的 `create_builtin_tool_registry()` 注册内置工具。

内置工具包括：

- `get_current_time`
- `paper_search`
- `pdf_parse`
- `kg_query`
- `kg_build`

论文精读 agent 实际暴露给模型的工具来自 `agent.profile.tools`：

```text
active_tool_names = list(agent.profile.tools)
tool_schemas = tool_registry.to_openai_tools(active_tool_names)
active_tool_name_set = set(active_tool_names)
```

对应代码在 `runtime/agent_runner.py:306` 附近。

为什么这样设计：

- registry 是“系统里有什么工具”。
- profile.tools 是“这个 agent 允许用什么工具”。
- tool schema 是“这次请求暴露给模型的工具说明”。
- 三者分离后，新增工具不会自动暴露给所有 agent，降低误调用风险。

### 8.9 工具如何被模型触发

工具触发在 `runtime/agent_runner.py:322-326`：

```text
response = model.chat(
    messages=messages,
    tools=tool_schemas,
    tool_choice="auto",
)
```

`tool_choice="auto"` 表示是否调用工具由模型决定。模型会根据：

- system prompt 里的 agent role 和 skill 指令
- user_content 里的当前论文上下文和用户问题
- tool schema 的 name/description/parameters

来决定是否返回 `tool_calls`。

如果模型没有返回 `tool_calls`：

```text
return build_result(get_message_content(assistant_message))
```

如果模型返回了 `tool_calls`：

```text
messages.append(to_assistant_message(assistant_message))
for tool_call in tool_calls:
    messages.append(run_tool_call(...))
```

然后进入下一轮 model.chat。最多循环 `max_steps` 次；论文精读 handler 调用时传的是 `max_steps=5`。

为什么这样设计：

- 兼容 OpenAI tool calling 标准。
- 工具结果以 `role="tool"` message 回灌，让模型基于真实工具结果继续生成最终回答。
- 多轮循环允许“先查论文/查 KG，再综合回答”。
- `max_steps` 限制可避免模型无限工具调用。

### 8.10 run_tool_call 如何保证工具安全执行

`run_tool_call()` 在 `runtime/agent_runner.py:153`。

它执行以下检查：

1. 从模型 tool call 中读取工具名：

```text
tool_name = get_tool_call_name(tool_call)
```

2. 解析 JSON 参数：

```text
arguments = parse_tool_arguments(...)
```

`parse_tool_arguments()` 在 `runtime/agent_runner.py:128`，能处理：

- `None`
- dict
- JSON string
- 非法 JSON string，返回 `_parse_error`

3. 检查工具名是否在本次 agent 允许列表中：

```text
if tool_name not in allowed_tool_names:
    raise PermissionError(...)
```

4. 从 registry 取工具：

```text
tool = tool_registry.get(tool_name)
```

5. 执行：

```text
tool_result = tool.run(arguments)
```

6. 把结果转成 tool message：

```text
{
  "role": "tool",
  "tool_call_id": ...,
  "content": json.dumps(tool_result, ensure_ascii=False)
}
```

为什么这样设计：

- 即使模型伪造了未暴露工具名，也会被 `allowed_tool_names` 拦截。
- 参数解析失败不会直接崩溃，而是作为工具参数里的 `_parse_error` 返回给工具/模型。
- 工具异常会被捕获并转为 `{ "error": "Tool execution failed: ..." }`，避免整个 agent 请求崩掉。
- 返回格式符合 OpenAI tool message 协议，便于模型继续推理。

### 8.11 论文精读四个工具分别做什么

#### 8.11.1 paper_search

实现位置：`tools/builtin/paper_search_tool.py`。

功能：

- 工具名 `paper_search`。
- 参数：`query`、`source`、`max_results`。
- 执行时临时创建 `PaperPipeline()`，调用 `pipeline.search()`。
- 返回论文标题、作者、年份、摘要、source、url、pdf_url。

适用场景：

- 用户要求查找相关论文。
- 跨论文对比或引用脉络需要补充外部论文线索。

设计注意：

- profile system prompt 已提示：如果已经通过 arXiv ID 找到目标论文，不要重复用标题检索。

#### 8.11.2 pdf_parse

实现位置：`tools/builtin/pdf_parse_tool.py`。

功能：

- 工具名 `pdf_parse`。
- 参数：`paper_id`、可选 `section_id`。
- 从 `PaperReadingStorage()` 读取已保存 paper。
- 如果指定 section，返回该 section 的标题、正文、长度、段落数量。
- 如果不指定 section，返回章节索引、标题、摘要。

适用场景：

- agent 需要主动拉取某个章节内容。
- 当前 prompt 里的章节内容不够，或用户追问另一个章节。

当前限制：

- 它创建新的 `PaperReadingStorage()` 读取本地持久化，而不是直接用 `app.state.paper_storage`。
- 它依赖 paper 已经被上传并保存。

#### 8.11.3 kg_query

实现位置：`tools/builtin/kg_query_tool.py`。

功能：

- 工具名 `kg_query`。
- 参数：`query_type`、`source_label`、`target_label`、`node_id`、`keyword/question`、`paper_id`。
- KG engine 通过 `set_kg_engine()` 注入。
- 支持：
  - `path`：实体关系路径。
  - `neighbors`：节点邻域。
  - `search`：调用 `KGQueryEngine.answer()` 做 KG 驱动问答。

适用场景：

- 用户问“这个方法和某个 baseline 什么关系”。
- agent 需要从图谱里找证据或路径。

#### 8.11.4 kg_build

实现位置：`tools/builtin/kg_build_tool.py`。

功能：

- 工具名 `kg_build`。
- 参数：`paper_id`、`section_id`、`section_content`、`mode`。
- KG builder 通过 `set_kg_builder()` 注入。
- 执行 `builder.ensure_full_paper_kg()`，再 `get_revealed_subgraph()`。
- 返回新增节点/边数量、节点摘要、section type、revealed KG。

适用场景：

- agent 读完某章节后希望确保 KG 已构建或获取当前阶段子图。

当前设计变化：

- 工具描述仍保留“读完章节后构建 KG”的语义。
- 实际 builder 现在是“整篇一次性构建 + 渐进展示”，所以 `kg_build` 内部也调用 `ensure_full_paper_kg()`。

### 8.12 start_reading 中 agent 输出如何进入 Skill 后处理与前端

业务入口在 `handlers/paper_reading/handler.py:221` 的 `_handle_start_reading()`。

关键步骤：

1. 创建或读取 session。
2. 加载 paper data。
3. 确保 KG 已构建，并按当前 section 取 revealed KG。
4. `_build_start_reading_context()` 构造 user_content。
5. `run_agent_detailed()` 调 agent。
6. `_active_skill_ids_for_context()` 决定后处理 skill ids。
7. `postprocess_agent_output()` 生成 `skill_outputs`。
8. `SessionManager.update_progress()` 标记章节完成。
9. 返回 payload 给前端。

`_build_start_reading_context()` 在 `handlers/paper_reading/handler.py:644`，它注入给 agent 的内容包括：

- paper_id、title、authors、abstract。
- session_id、current_section、active_skills、progress。
- 论文目录。
- 当前章节正文，最多约 9000 字符。
- 已展开 KG 摘要。
- 用户问题。

这解释了为什么 agent 可以回答“当前章节”的问题：不是工具先拉正文，而是 handler 已经把当前章节正文放进 user_content 了。

`_active_skill_ids_for_context()` 在 `handlers/paper_reading/handler.py:739`，逻辑是：

```text
if active_skills:
    return active_skills
if current section 是 experiment/result:
    return reading.critique_agent
if current section 是 conclusion:
    return reading.idea_generator
else:
    return reading.method_analyst
```

这个返回值用于后处理，不等同于 system prompt 注入。

### 8.13 Skill 输出后处理与前端展示链路

`postprocess_agent_output()` 在 `handlers/paper_reading/postprocessors/postprocess.py`。

它按 skill id 路由到不同 processor，例如：

- `reading.method_analyst -> method_analyst.postprocess`
- `reading.math_verifier -> math_verifier.postprocess`
- `reading.critique_agent -> critique_agent.postprocess`

每个 processor 通常会：

1. 用 `extract_json_object(text)` 从 agent 文本中找 JSON。
2. 如果成功，把 JSON 作为 `content`。
3. 用 `render_dict_markdown()` 生成 `rendered`。
4. 生成 `kg_candidates`。
5. 返回 `SkillOutput-like dict`。

例如：

- `method_analyst` 会读取 `data.pipeline[]`，生成 `Module` 节点候选。
- `math_verifier` 会读取 `data.formula`，生成 `Concept` 节点候选。

前端收到后：

- `applyReadingPayload()` 保存 `state.skillOutputs`。
- `renderSkillOutputs()` 创建 `skill-output-card`。
- 如果 `output_type === "math_derivation"`，走 `renderMathTabs()`。
- 否则走通用结构化渲染或 Markdown 渲染。
- 如果有 `kg_candidates`，显示候选数量。

当前边界：

- 后处理生成的 `kg_candidates` 还没有确认写入 KG 的后端 action。
- 后处理能否结构化展示取决于 agent 是否按 skill 要求输出 JSON；否则会 fallback 到 raw text。

### 8.14 为什么整体设计成“Action Handler + Agent Runner + Registry + Selector + Tool Calling”

这个设计有几个明显目标：

1. 统一入口，便于前端简单调用。

   论文精读所有请求都走 `POST /paper_reading`，用 action 路由。这让前端只维护一个 `callPaperReading()`，不用管理很多 URL。

2. 业务上下文由 handler 组装，agent 只负责推理。

   `_handle_start_reading()` 先把论文、章节、KG、进度整理好，再交给 agent。这样 agent 不需要知道存储细节，也不需要每次都工具调用才能拿到当前章节。

3. Skill 是可扩展 prompt 能力，不是硬编码 agent 分支。

   `SKILL.md` 通过 registry 管理，selector 动态选择，新增 skill 理论上只需要加文件和 profile 配置。

4. 工具是受控能力，不是任意函数调用。

   工具必须实现 `BaseTool`，必须注册到 registry，还必须出现在 agent profile 白名单中，最后模型返回 tool call 时还要通过 `allowed_tool_names` 校验。

5. Tool calling 与 skill 解耦。

   Skill 改变“怎么思考和输出”，Tool 改变“能访问什么外部/结构化能力”。二者在 `run_agent_detailed()` 中组合，但生命周期独立。

6. 前端展示与 agent 原文解耦。

   后处理器把 agent 文本转为 `skill_outputs`，前端可以展示结构化卡片；即使 JSON 解析失败，也能展示 raw Markdown。

### 8.15 当前设计的关键不足与可改进点

1. 手动 load skill 没有直接强制 system prompt 注入。

   当前 `session.active_skills` 主要影响上下文和后处理。若要更符合用户直觉，可以让 `_handle_start_reading()` 把 `session.active_skills` 传给 `run_agent_detailed()`，并在 `resolve_runtime_capabilities()` 中优先加载这些 skill，而不是只依赖 selector。

2. Skill selector 与 active skill 可能选择不一致。

   例如用户手动激活 `reading.math_verifier`，selector 仍可能根据 user_content 选择 `reading.domain_expert` 或 null。最终后处理走 math_verifier，但 system prompt 不一定包含 math_verifier 的完整指令。

3. Tool registry 的部分工具重新创建 storage/pipeline。

   `pdf_parse` 和 `kg_build` 内部创建新的 `PaperReadingStorage()`，不是从 `app.state` 注入。这简化了工具接口，但会让依赖管理不如 KG engine/builder 一致。

4. 工具 schema 暴露给模型，但业务 handler 已经预先注入很多上下文。

   这能减少工具调用次数，但模型什么时候该用 `pdf_parse` 或 `kg_query` 主要靠 prompt 和 tool description，缺少更强的 planner。

5. Skill 输出结构化依赖模型自觉输出 JSON。

   postprocessor 有 JSON 抽取兜底，但没有强 schema 修复或重试，所以复杂 skill 卡片可能退化为 raw text。

## 9. 结论与当前实现边界

当前论文精读模块已经形成一个完整可运行的工作台闭环：导入论文、解析重排、创建 session、调用 agent 精读、按章节记录进度、加载 skill、Fork 深挖、构建和查询 KG。

但它的关键边界也很清楚：

- 论文重排质量高度依赖 PyMuPDF 文本块顺序和正则启发式，因此双栏、脚注、公式、表格、复杂图文混排会不稳。
- PDF 原文模式只是 iframe 查看，不具备 selection -> skill 分析链路。
- Skill 加载在产品语义上已经做了，但工程语义上“active skill”主要影响上下文和后处理；真正强制专项分析仍依赖前端把 skill prompt 放入 `content` 或 Fork 上下文。
- KG 已经是 NetworkX DiGraph + Cytoscape-style elements 的完整结构，但前端展示是手写 SVG；KG 候选从 Skill 输出到正式写入图谱的闭环还缺最后确认 action。

如果下一步优先解决你提到的重排错误，应优先改 `PDFParser` 的版面分析、公式/表格/脚注模型和坐标级 section 归属，而不是先改前端渲染。
