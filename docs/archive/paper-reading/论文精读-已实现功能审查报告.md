# 论文精读已实现功能审查报告

> 审查日期: 2026-07-21  
> 审查范围: `paper_reading/`、`handlers/paper_reading_handler.py`、`channels/web.py`、`gateway/static/`、`tools/builtin/`、`skills/builtin/reading/`、相关 docs 与测试脚本  
> 审查方式: 本次无法使用用户提到的 `review-agent` skill（当前可用 skill 列表中不存在该 skill），因此采用代码审查 + 文档对照 + smoke check 的方式完成。

## 1. 总体结论

当前论文精读模块处于“骨架和局部能力可导入、可单测”的阶段，尚未达到 `论文精读.pdf/docx` 描述的完整论文精读成品状态。

已经完成且基本正确的部分包括：

- `PaperReadingRequest` / `PaperReadingResponse` schema 骨架。
- 12 个 action 的 handler 路由框架。
- 论文搜索、PDF 解析、KG 查询、KG 构建 4 个 tool 的注册和基础实现。
- 13 种 KG 节点、9 种 KG 边、`KnowledgeGraphEngine` 基础 CRUD/查询/Cytoscape 导出。
- `SessionManager`、Checkpoint、Fork/Merge、Storage 的基础结构。
- 8 个 `skills/builtin/reading/*/SKILL.md` 已存在，并能被 skill registry 发现。

但端到端 API 目前不符合预期。最大阻断点在 Web channel: `channels/web.py` 只把 `body.content` 传给 handler，而论文精读 handler 期待的是完整 `{action, paper_id, search_query, pdf_url, kg_* ...}` 请求体。因此按文档调用 `/paper_reading` 时，多数 action 字段会在进入 handler 前丢失。

## 2. 关键问题

### 2.1 严重: WebChannel 丢失论文精读请求体

位置: `channels/web.py:57-60`

```python
return self.create_inbound_message(
    session_id=self._read_session_id(body),
    content=str(body.get("content") or ""),
    mode=mode,
    ...
)
```

位置: `paper_reading/handler.py:53-56`

```python
content = message.content
if isinstance(content, str):
    content = json.loads(content)
request = PaperReadingRequest.model_validate(content)
```

影响:

- 文档要求发送 `{"action": "search_paper", "search_query": "...", ...}`。
- 实际进入 handler 的只有 `content` 字符串。
- 如果 `content` 是普通自然语言，会触发 JSON 解析失败。
- 如果 `content` 为空，会触发 JSON 解析失败。
- `search_query`、`pdf_url`、`paper_id`、`target_section`、`kg_question` 等 action 字段不会传入 handler。

结论: 当前 `/paper_reading` 的 Web/API 通道与 `PaperReadingRequest` 协议没有接上。

### 2.2 严重: `session_id` 被 WebChannel 强制要求必填

位置: `channels/web.py:74-77`

```python
session_id = str(body.get("session_id") or "").strip()
if not session_id:
    raise HTTPException(status_code=400, detail="session_id is required.")
```

影响:

- `PaperReadingRequest.session_id` 默认允许为空字符串。
- 文档中也说明首次请求为空时系统自动创建会话。
- 但 WebChannel 会在 handler 前直接返回 400。

结论: 首次阅读、首次上传、首次搜索等流程与文档预期不一致。

### 2.3 KG 渐进构建仍是占位实现

位置: `paper_reading/kg/builder.py`

当前只有 Abstract 会创建两个占位节点:

- `Problem` label 固定为 `Research Problem`
- `Method` label 固定为 `Proposed Method`

以下章节构建方法仍返回空节点和空边:

- `_build_introduction_kg()`
- `_build_method_kg()`
- `_build_experiment_kg()`
- `_build_conclusion_kg()`
- `_build_general_kg()`

结论: 需求文档中 “Introduction 创建 Baseline/RelatedWork”、“Method 创建 Module/Concept”、“Experiment 创建 Experiment/Dataset/Metric”、“Conclusion 创建 Limitation/Claim” 尚未真正实现。

### 2.4 `kg_query` 不是完整 KG 驱动问答

位置: `paper_reading/handler.py:371-401`

当前行为:

- `path`: 调用 `kg_engine.query_path()`
- `neighbors`: 调用 `kg_engine.get_neighbors()`
- 其他: 调用 `kg_engine.search_nodes()`
- 可附加 `cytoscape_elements`

缺失内容:

- 没有实体抽取。
- 没有多跳 reasoning path 组织。
- 没有结合 LLM 生成自然语言回答。
- 没有返回需求中的 `{answer, reasoning_paths, evidence}` 完整结构。

结论: 当前是基础图查询，不是需求文档中的 KG 驱动智能问答。

### 2.5 `start_reading` 上下文不足

位置: `paper_reading/handler.py:192-259`

当前传给 agent 的主要内容只有:

```text
当前章节: {current_section}
{用户 content}
```

缺失内容:

- 当前论文标题、摘要、章节正文。
- 已解析 sections 的上下文。
- 已有 KG 摘要。
- 当前 active skills 的上下文。
- 会话历史。
- 阅读进度中更细粒度的位置。

结论: 即使 LLM 正常可用，Agent 也缺少精读所需的论文原文和结构化上下文。

### 2.6 Skill 只有 prompt 定义，缺少 Python 后处理

现状:

- 8 个 `SKILL.md` 已存在。
- `SkillRegistry` 能发现它们。
- `runtime/agent_runner.py` 能把默认 skill 和一个被选择的专项 skill 拼入 system prompt。

缺失:

- `paper_reading/skills/*.py` 后处理逻辑尚未实现。
- 没有解析各 skill 约定的 JSON 输出。
- 没有把 skill 输出稳定转换为 `SkillOutput`。
- 没有把 skill 结果写入 KG 或前端可消费结构。

结论: Skill 框架接入了 prompt 层，但业务结果结构化和可视化承接尚未完成。

## 3. 当前真实返回结构

`gateway/message_flow.py` 会把 handler 返回的 dict 包进 `ChannelMessage.content`，因此 HTTP 响应顶层不是直接的 `PaperReadingResponse`，而是:

```json
{
  "session_id": "...",
  "channel": "web",
  "direction": "outbound",
  "mode": "paper_reading",
  "content": {
    "status": "ok|error",
    "action": "...",
    "data": {},
    "session": {},
    "progress": {}
  }
}
```

注意: 以下结构是 `paper_reading/handler.py` 的理论输出。由于当前 WebChannel 丢失完整请求体，多数 action 在真实 `/paper_reading` 路径下无法按文档正常触发。

## 4. 前端展示建议

当前 `gateway/static/app.js` 只是通用聊天页:

- 模式选择包括 `paper_reading`。
- 发送体只有 `{session_id, content, user_id, metadata}`。
- 没有传 `action`。
- 没有论文搜索、上传、章节导航、Skill 面板、KG 图谱、Fork 弹窗。
- `extractReply()` 会优先把整个 `response.content` JSON stringify 出来，不能细分渲染论文精读结果。

建议论文精读前端独立实现为专用页面，而不是继续沿用通用聊天页。

### 4.1 推荐布局

采用需求文档中的三栏 + 底部 KG:

- 左侧: 论文导航与进度
  - 搜索/上传入口。
  - 论文 Outline。
  - 章节阅读状态。
  - Skill 加载入口。
- 中间: 论文正文
  - PDF/结构化文本渲染。
  - 当前章节定位。
  - KG 节点高亮。
  - 点击段落或公式触发解释/Fork。
- 右侧: AI 专家面板
  - Method Analyst 输出。
  - Critique Agent 输出。
  - Math Verifier 输出。
  - Domain Expert / Writing Coach / Idea Generator 输出。
- 底部: KG 可视化
  - 使用 Cytoscape.js 或等价图组件。
  - 消费 `kg_query.data.cytoscape_elements`。
  - 点击节点联动正文与右侧详情。

### 4.2 后端返回到 UI 的映射

| 后端字段 | 前端展示位置 |
|---|---|
| `search_paper.data.papers` | 搜索结果列表/论文卡片 |
| `upload_paper.data.sections` | 左侧 Outline |
| `upload_paper.data.title/authors/abstract` | 论文头部元信息 |
| `start_reading.data.agent_response` | 右侧 AI 回复卡片 |
| `start_reading.session.active_skills` | Skill 面板激活状态 |
| `progress` | 左侧进度条与章节状态 |
| `kg_query.data.cytoscape_elements` | 底部 KG 图谱 |
| `fork.data.fork_session_id` | Fork 子会话弹窗 |
| `merge.data.key_findings` | 主阅读流合并摘要 |

### 4.3 前端请求建议

前端不应继续只发纯聊天消息，而应按 action 构造请求体:

```json
{
  "action": "start_reading",
  "session_id": "...",
  "paper_id": "...",
  "target_section": "sec:3.2",
  "content": "请解释这个模块为什么必要"
}
```

响应解析应读取:

```js
const payload = response.content;
if (payload.status === "error") {
  // render error
}
switch (payload.action) {
  case "search_paper":
    renderPaperResults(payload.data.papers);
    break;
  case "upload_paper":
    renderOutline(payload.data.sections);
    break;
  case "start_reading":
    renderAgentPanel(payload.data.agent_response);
    renderProgress(payload.progress);
    break;
}
```

## 5. 测试与验证记录

已执行验证:

1. 直接运行:

```powershell
python tests\test_paper_reading\verify_imports.py
```

结果: 失败，原因是当前环境未安装项目且未设置 `PYTHONPATH`，报 `ModuleNotFoundError: No module named 'paper_reading'`。

2. 设置 `PYTHONPATH=.` 后运行:

```powershell
$env:PYTHONPATH='.'
python tests\test_paper_reading\verify_imports.py
```

结果: 失败，原因是 Windows 默认 GBK 控制台无法输出进度文本中的 emoji，报 `UnicodeEncodeError`。

3. 设置 UTF-8 后运行:

```powershell
$env:PYTHONPATH='.'
$env:PYTHONIOENCODING='utf-8'
$env:PYTHONUTF8='1'
python tests\test_paper_reading\verify_imports.py
```

结果: 通过，输出 `ALL 13 CHECKS PASSED`。

该 smoke check 能证明:

- schema 可导入。
- KG model/engine/builder/fusion 基础构造可运行。
- session/fork/progress 基础构造可运行。
- 4 个论文 tool 和 tool registry 可注册。
- 8 个 SKILL.md 可发现。
- paper_reading agent profile 存在。

该 smoke check 不能证明:

- `/paper_reading` HTTP 端到端正确。
- WebChannel 会保留完整 action 请求体。
- 搜索/上传/PDF 解析在真实依赖下可用。
- LLM 调用与 tool loop 能稳定完成论文精读。
- KG 能按章节真实生成语义节点和边。
- 前端能正确渲染论文精读结果。
