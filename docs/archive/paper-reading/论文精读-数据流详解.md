## 1. 全景概览

用户通过 Web UI 或 curl 发送一个请求，经过以下 **8 个阶段**，最终得到论文精读 Agent 的回复：

```
用户
  │ POST /paper_reading
  │ {"action":"start_reading", "paper_id":"...", "content":"分析这篇论文的核心创新"}
  ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ Phase 1: gateway/app.py                                                │
│   FastAPI 路由 → 调用 process_channel_input()                          │
├─────────────────────────────────────────────────────────────────────────┤
│ Phase 2: gateway/message_flow.py                                       │
│   process_channel_input() → process_channel_message()                  │
│   统一消息管道: inbound → handler → outbound                            │
├─────────────────────────────────────────────────────────────────────────┤
│ Phase 3: channels/web.py                                               │
│   WebChannel.receive_message() → ChannelMessage(direction="inbound")    │
│   把 HTTP JSON 请求体 转换为 系统内部统一消息格式                           │
├─────────────────────────────────────────────────────────────────────────┤
│ Phase 4: paper_reading/handler.py                                      │
│   handle_paper_reading_message() → 解析 action → 路由到子处理器           │
│   _handle_start_reading(): 创建/恢复会话 → 调用 run_agent_detailed()     │
├─────────────────────────────────────────────────────────────────────────┤
│ Phase 5: runtime/agent_runner.py                                       │
│   run_agent_detailed() → resolve_runtime_capabilities()                │
│   加载 Default Skill + 选择 Special Skill → 拼接 system_prompt           │
├─────────────────────────────────────────────────────────────────────────┤
│ Phase 6: skills/registry.py + skills/selector.py                       │
│   SkillRegistry: 从 SKILL.md 文件加载 Skill 指令                         │
│   CapabilitySelector: 用小模型调用选择 0~1 个专项 Skill                   │
├─────────────────────────────────────────────────────────────────────────┤
│ Phase 7: models/client.py + tools/registry.py                          │
│   OpenAIClient.chat() → LLM API 调用                                    │
│   LLM 返回 tool_calls → ToolRegistry.run() → 结果返回 LLM               │
├─────────────────────────────────────────────────────────────────────────┤
│ Phase 8: 回程                                                            │
│   handler 返回 dict → build_channel_output() → ChannelMessage(outbound) │
│   → bus 记录 → HTTP Response                                           │
└─────────────────────────────────────────────────────────────────────────┘
用户
  ◄ JSON Response
  {"status":"ok", "data":{"agent_response":"这篇论文的核心创新在于..."}}
```

## 3. Phase 1: HTTP 请求进入

**发生时机**: 用户每次发送请求时

**入口文件**: [gateway/app.py:77](../gateway/app.py#L77)

### 3.1 路由注册

```python
# gateway/app.py:77
@app.post("/paper_reading")
async def paper_reading(request: Request) -> ChannelMessage:
    return await process_channel_input(
        source=request,             # FastAPI Request 对象（原始 HTTP 请求）
        mode="paper_reading",       # 功能模式标识
        handler=handle_paper_reading_message,  # ★ 指向 handlers/paper_reading_handler.py
        app_state=request.app.state,           # ★ 共享状态（所有组件都在这里）
    )
```

**这段代码做了什么**:
1. FastAPI 监听到 `POST /paper_reading` HTTP 请求
2. 从 `request.app.state` 获取所有共享组件
3. 指定 handler 为 `handle_paper_reading_message`
4. 交给 `process_channel_input()` 统一处理

**为什么不直接在路由里写逻辑？**  
因为未来可能有 QQ 等其他 channel。`process_channel_input` 是**平台无关的统一消息管道**，Web 和 QQ 走同一套流程，只换 channel 适配器。

│

## 5. Phase 3: Channel 适配

**入口文件**: [channels/web.py](../channels/web.py)

### 5.1 WebChannel.receive_message()

```python
# channels/web.py:52
async def receive_message(self, source: Request, mode: str) -> ChannelMessage:
    request = source
    body = await request.json()       # 解析 HTTP JSON body
    # body = {"action":"start_reading", "paper_id":"...", "content":"...", "session_id":"..."}

    return self.create_inbound_message(
        session_id=self._read_session_id(body),  # 从 body 提取 session_id（必填）
        content=str(body.get("content") or ""),   # ★ 用户的实际输入
        mode=mode,                                 # "paper_reading"
        user_id=body.get("user_id"),
        metadata=body.get("metadata"),
    )
```

### 5.2 ChannelMessage 结构

```python
# channels/base.py:15
@dataclass(slots=True)
class ChannelMessage:
    session_id: str          # "abc123"
    channel: str             # "web"
    direction: str           # "inbound" / "outbound"
    mode: str                # "paper_reading"
    content: Any             # ★ 核心数据 — 用户输入/系统输出
    user_id: str | None      # None
    metadata: dict           # {}
    message_id: str          # UUID
    created_at: datetime     # UTC timestamp
```

**关键点**: `content` 字段是 **Any 类型**。入站时它是用户发的 JSON dict（如 `{"action":"start_reading", ...}`），出站时它是 handler 返回的 dict（如 `{"status":"ok", ...}`）。Channel 不关心 content 是什么结构，只负责传递。

### 8.2 Skill 选择失败时的降级策略

```
如果 CapabilitySelector 调用失败（网络错误/JSON 解析失败/选择的 skill 不在允许列表）:
  → 记录 warning 日志
  → 只用 [Agent Role] + [Default Skill]（不加载 Special Skill）
  → 请求继续进行，不会崩溃

如果 SkillRegistry 加载失败:
  → 记录 warning 日志
  → 只用 [Agent Role]（连 Default Skill 也不加载）
  → 请求继续进行，不会崩溃
```

**设计哲学**: Skill 是"锦上添花"，不是"不可或缺"。任何 Skill 环节出错，系统都能降级到最基本的 Agent Role 继续工作。
