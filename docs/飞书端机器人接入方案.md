# 飞书端机器人接入方案

> 接入形态：飞书企业自建机器人 WebSocket 长连接；统一消息模型：`ChannelMessage`；业务模式：`chat`、`domain_onboarding`、`paper_reading`。本文说明当前飞书端的功能边界、实现链路和主要技术难点。

## 功能介绍

飞书端作为 NoviceSynapse 的外部 Channel Adapter，负责飞书事件与统一消息之间的转换。科研能力仍由现有 Handler、Agent、领域入门 Pipeline 和论文精读流程提供。

| 功能 | 用户侧行为 | 后端复用 |
| --- | --- | --- |
| 日常聊天 | 发送普通文本并获得机器人回复 | `handle_chat_message` |
| 领域入门 | 输入研究领域，直接返回入门卡片正文 | `handle_domain_onboarding_message` |
| 论文精读 | 支持论文链接和飞书 PDF 文件 | `handle_feishu_mode_message` 及论文精读流程 |
| 模式切换 | 支持日常聊天、领域入门、论文精读 | `parse_mode_switch` 和会话模式状态 |
| 模式与正文同条提交 | 切换模式后立即处理同条消息的正文 | `remaining_content` 路由 |
| 处理状态提示 | 领域入门和论文解析期间先发送等待提示 | `_send_status_message` |
| 对话入库 | 飞书消息和正式回复可在网页资料库查看 | `process_channel_message` |
| 纯文本输出 | 清理 Markdown 源码并保留可读结构 | `format_plain_text` |
| 文件下载 | 通过飞书消息资源接口获取 PDF 字节 | `_download_message_file` |

典型使用方式如下：

```text
日常聊天
切换到日常聊天模式
领域入门
切换到领域入门模式，大模型
/入门 多智能体系统
论文精读
/论文 https://arxiv.org/abs/1706.03762
```

领域入门回复只显示卡片正文，不附加“前往网页端查看”或网页地址。论文精读和日常聊天中的必要论文链接仍然保留。

## 实现方式

### 整体链路

```text
飞书 im.message.receive_v1 事件
  → FeishuChannel._on_message
  → ChannelMessage(channel="feishu")
  → 后台消息处理线程
  → 模式识别与业务路由
  → process_channel_message
  → 资料库存储
  → FeishuChannel.send_outbound
  → 飞书消息创建接口
```

飞书 WebSocket 回调只完成事件校验、去重和标准化，耗时的模型或论文处理交给后台线程，避免阻塞 SDK 的事件分发线程。

### 启动与配置

Gateway 通过配置文件或环境变量解析飞书连接信息，环境变量优先：

| 配置 | 用途 |
| --- | --- |
| `FEISHU_APP_ID` / `LARK_APP_ID` | 飞书应用 App ID |
| `FEISHU_APP_SECRET` / `LARK_APP_SECRET` | 飞书应用 App Secret |
| `channels.feishu.enabled` | 是否启用飞书 Channel |
| `channels.feishu.app_id` | 配置文件中的 App ID |
| `channels.feishu.app_secret` | 配置文件中的 App Secret |

启用飞书时必须同时提供 App ID 和 App Secret，否则 Gateway 在启动阶段报配置不完整。配置有效时，`FeishuChannel` 被注册到 `app.state.channels`，并由统一启动循环调用 `start()`。

SDK 初始化包含两个客户端：

1. `lark.ws.Client`：接收 WebSocket 事件；
2. `lark.Client`：发送消息和下载消息资源。

事件处理器订阅 `im.message.receive_v1`，当前只接收 `text` 和 `file` 类型。

### 消息标准化

文本消息从飞书 JSON `content` 中提取 `text`；文件消息提取 `file_key` 和 `file_name`。之后构造：

```python
ChannelMessage(
    session_id="<chat_id>",
    channel="feishu",
    direction=INBOUND,
    mode="chat | domain_onboarding | paper_reading",
    content="文本或文件信息",
    user_id="<sender open_id/user_id/union_id>",
    metadata={
        "chat_id": "...",
        "feishu_message_id": "...",
        "message_type": "text | file",
    },
)
```

`chat_id` 作为飞书会话 ID，同时用于模式状态和机器人回复目标；`feishu_message_id` 用于事件去重及文件资源下载。

### 模式切换与业务路由

飞书按 `chat_id` 保存当前业务模式，默认值为 `chat`。自然语言模式解析由 `parse_mode_switch` 完成，Channel 额外补充“日常聊天”命令及其同条正文形式。

模式切换分为两种：

1. 纯切换：更新模式并返回“已切换到……”；
2. 切换加正文：更新模式，将 `remaining_content` 写回消息后继续调用新模式 Handler。

正式路由关系如下：

| `mode` | 处理方式 |
| --- | --- |
| `chat` | 通过 `handle_feishu_mode_message` 进入日常聊天 Handler |
| `domain_onboarding` | 直接调用 `handle_domain_onboarding_message`，返回完整入门内容 |
| `paper_reading` | 通过 `handle_feishu_mode_message` 处理论文 URL 或文件 |

领域入门绕过“网页入口型”平台路由，直接调用完整卡片 Handler，防止回复被压缩成摘要加网页地址。

### 状态提示与正式回复

领域入门开始前发送：

```text
正在思考中，请稍候...
```

论文模式只有在收到文件或 URL 时发送：

```text
正在读取并解析论文，请稍候...
```

状态提示直接调用飞书消息接口，不进入 `process_channel_message`，因此不会被误记为正式业务回复。最终生成结果仍经过统一消息流并写入资料库。

### PDF 文件适配

飞书文件消息只包含 `file_key`，不能直接交给论文 Pipeline。下载流程为：

```text
feishu_message_id + file_key
→ GetMessageResourceRequest(type="file")
→ 飞书消息资源接口
→ bytes
→ 论文上传、解析和精读流程
```

下载方法检查 `message_id`、`file_key`、接口状态和响应文件对象，并保证最终返回 `bytes`。文件格式与论文输入规则继续由论文路由及后续流程校验。

### 资料库与消息持久化

飞书正式消息复用公共 `process_channel_message`：

```text
publish inbound
→ record inbound
→ execute handler
→ build outbound
→ record outbound
→ send outbound
```

网页资料库可根据 `channel="feishu"`、`session_id=<chat_id>`、业务模式和平台消息 ID 查看飞书端对话。处理中状态提示不入库，避免资料库出现与真实回答无关的临时消息。

### 输出格式与网址策略

飞书当前使用 `msg_type="text"`，不会完整渲染模型生成的 Markdown。因此 `_format_output` 会：

- 从字符串或字典的 `content`、`text`、`answer`、`message` 字段提取正文；
- 删除 Markdown 标题、强调、代码围栏和链接语法；
- 将表格、LaTeX 和多行 JSON 转换为普通文本；
- 日常聊天和论文精读保留正常网址；
- 领域入门删除网址，并额外删除“详细入门路线请在网页端查看”等完整跳转提示。

最终调用飞书消息创建接口，以 `receive_id_type="chat_id"` 把文本发送到原会话。

## 技术难点

### WebSocket 回调不能被模型调用阻塞

领域入门和论文解析可能持续较长时间。如果直接在 `_on_message` 内运行 Handler，会阻塞飞书 SDK 的事件线程并影响后续事件接收。

当前做法是回调完成去重和消息转换后，为每条消息启动后台线程。该方案适合当前单机部署；流量增大后应改为受控线程池或任务队列，避免大量并发消息创建过多线程。

### 重复事件与正式回复幂等

飞书可能重复投递同一个 `message_id`。重复执行会造成重复模型调用、重复回复和重复入库。

当前以最近 1000 个 `feishu_message_id` 在进程内去重。多 Gateway 副本部署时必须使用共享幂等存储，并让消息记录层对平台事件 ID 建立唯一约束。

### 文件资源下载依赖双重标识

飞书文件下载同时依赖原消息 ID 和 `file_key`。如果标准化阶段遗漏 `feishu_message_id`，或者路由过程中丢失 metadata，文件下载会失败。

当前把这两个标识分别保存在 `metadata` 和 `content` 中，下载回调由论文路由按统一约定调用。该设计保持业务层不感知飞书 SDK，但要求 ChannelMessage 在整个流程中完整传递 metadata。

### 模式切换与会话隔离

模式以 `chat_id` 为键，能隔离不同私聊或群聊会话，但当前状态仅保存在内存。服务重启后所有会话恢复到 `chat`；多进程部署时，不同进程也可能观察到不同模式。

若需要跨重启保持模式，应将其写入统一会话存储，并为并发切换增加版本或原子更新机制。

### 入门卡片正文与网页入口解耦

领域入门 Handler 的完整结果适合网页展示，但机器人端要求直接返回正文，不能只发送摘要和网页地址。若统一经过带平台提示的 Router，容易把回答改写为“请前往网页端查看”。

当前在业务路由阶段直接调用 `handle_domain_onboarding_message`，在输出阶段再按模式删除网址和历史网页提示。两层防护分别解决“结果被替换”和“旧提示残留”，且不影响论文精读中的正常链接。

### Markdown 与飞书消息类型不一致

飞书文本消息不会按网页规则渲染 Markdown。直接发送模型结果会出现 `###`、`**`、代码围栏、LaTeX 分隔符和 Markdown 表格源码。

当前统一降级为可读纯文本。若后续需要更好的视觉效果，可把结构化结果映射为飞书富文本或交互卡片，但必须处理卡片大小限制、字段截断、更新机制和降级文本。

### 状态提示与资料库一致性

“正在思考中”属于平台交互反馈，不是科研结果。如果它也走统一持久化链路，网页资料库会多出无意义的助手消息。

实现将状态提示与正式业务回复分开：状态提示直接发送，正式回复才走 `process_channel_message`。如果状态发送失败，只记录日志，不中断科研任务。

### 部署边界

- 当前支持文本和文件消息，不处理图片、音频或其他飞书消息类型。
- 当前以普通文本回复，不包含飞书交互卡片的增量更新。
- WebSocket 异常停止时会记录错误；生产环境应由进程守护或连接监督机制保证恢复。
- 会话模式和去重集合为进程内状态，默认适用于单 Gateway 进程。
- App Secret 应通过安全配置注入，不应写入代码、文档示例或日志。
- 多副本部署前需引入共享会话状态、幂等存储和受控任务队列。
