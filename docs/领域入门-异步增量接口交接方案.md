# 领域入门异步增量接口交接方案

> 输出 Schema：`domain-onboarding-output-v1.10`；质量策略：`domain-quality-v1.8.0`。本文定义后端契约与前端消费方式。

## 接口

1. `POST /domain_onboarding/jobs`：提交任务，返回 `202`、`task_id` 和仅用于该任务的 `access_token`。`client_request_id` 用于幂等重试。
2. `GET /domain_onboarding/jobs/{task_id}/events`：SSE 事件流。使用 `Last-Event-ID` 或 `?after=<id>` 从断点回放。
3. `GET /domain_onboarding/jobs/{task_id}`：完整快照，用于首次打开、SSE 不可用时轮询和断线后校准。
4. `DELETE /domain_onboarding/jobs/{task_id}`：设置 `cancel_requested` 并发布可观测的取消事件。已在进行的同步模型/网络调用会先返回，然后 Pipeline 在下一阶段边界停止。
5. `POST /domain_onboarding/jobs/{task_id}/retry`：为 `failed` / `cancelled` / `interrupted` 任务创建新任务，并通过 `parent_task_id` 保留审计关系。
6. `POST /domain_onboarding`：保留一个版本的旧同步接口。

除创建接口外，查询、SSE、取消和重试均需携带：

```http
Authorization: Bearer <access_token>
```

原生 `EventSource` 无法自定义 Authorization Header 时，可使用 `?access_token=<token>`；生产前端更推荐用 `fetch` 读取 SSE，避免令牌进入 URL 日志。任务不存在或令牌错误统一返回 `404`，不暴露任务是否存在。

完整请求示例：[domain-onboarding-incremental-request-v1.5.json](examples/domain-onboarding-incremental-request-v1.5.json)。

完整任务快照示例：[domain-onboarding-incremental-response-v1.5.json](examples/domain-onboarding-incremental-response-v1.5.json)。

完整 SSE 事件流示例：[domain-onboarding-incremental-events-v1.5.jsonl](examples/domain-onboarding-incremental-events-v1.5.jsonl)。两个文件均来自 2026-07-29 的受控真实请求，并由当前评估器重算通过；不包含人工填写的摘要、质量分或硬门槛结果。

提交成功后的首个响应为：

```json
{
  "task_id": "8f4a2d31-64a8-4fc7-93c8-7704bf12c201",
  "state": "queued",
  "revision": 1,
  "access_token": "<create-response-only>",
  "poll_url": "/domain_onboarding/jobs/8f4a2d31-64a8-4fc7-93c8-7704bf12c201",
  "events_url": "/domain_onboarding/jobs/8f4a2d31-64a8-4fc7-93c8-7704bf12c201/events",
  "cancel_url": "/domain_onboarding/jobs/8f4a2d31-64a8-4fc7-93c8-7704bf12c201"

```

SSE 中一条可回放事件的完整格式为：

```text
id: 5
event: development_ready
data: {"id":5,"task_id":"8f4a2d31-64a8-4fc7-93c8-7704bf12c201","revision":5,"event":"development_ready","progress":0.58,"provisional":true,"replace_paths":["domain","text","learner_profile","prerequisites","development_stages","papers"],"data":{"domain":"检索增强生成","text":"...","learner_profile":{},"prerequisites":[],"development_stages":[],"papers":[]}}
```

## 事件顺序与展示

| 事件 | 建议展示 | `replace_paths` |
| --- | --- | --- |
| `accepted` | 任务已接收 | `[]` |
| `profile_ready` | 学习者画像 | `learner_profile` |
| `plan_ready` | 调研视角与检索词 | `research_plan` |
| `papers_ready` | 已验证论文候选 | `papers` |
| `stage_plan_ready` | 按时间组织的发展阶段提纲 | `research_plan` |
| `stage_retrieval_ready` | 某个发展阶段的论文检索与绑定完成 | `research_plan` |
| `development_ready` | 概述、前置知识和领域历史演进 | 多个顶层路径 |
| `landscape_ready` | 当前问题与子方向全景 | `current_landscape` |
| `learning_path_ready` | 标准新手学习路线与复现产物 | `learning_path` |
| `quality_ready` | 首轮质量结果，仍可能触发修复 | `quality` |
| `final_quality_ready` | 最终选中版本的质量结论 | `final_quality` |
| `repair_started` | 显示“正在修复” | `[]` |
| `cancel_requested` | 显示“取消中，将在当前调用返回后停止” | `[]` |
| `section_replaced` | 修复结果被选中后，定向替换受影响分区 | 具体变更路径 |
| `completed` | 以 `result` 替换所有临时内容 | `result` |
| `failed` / `cancelled` | 保留已生成部分，显示重试或取消状态 | 见事件 |

每条事件都含 `id`、`task_id`、`revision`、`event`、`progress`、`provisional`、`replace_paths` 和 `data`。前端只应接受更大的 `revision`，根据 `replace_paths` 原子替换结构化分区，不拼接半截 JSON。

`progress` 是阶段进度，不是剩余时间估计。终态完整 `result` 只在任务快照中持久化一次；SSE 发送或断点回放 `completed` 时由 Gateway 从快照动态补全，避免 SQLite 重复存储整份结果。

## 状态、断线和重启

- `queued` / `running` / `cancel_requested` 是非终态；`completed` / `failed` / `cancelled` / `interrupted` 是终态。
- SSE 断开不会取消任务。重连时带上最后一个事件 ID；如果事件流不可用，按 2–5 秒轮询快照。
- Gateway 重启后，未完成任务标记为 `interrupted` 且 `retryable=true`，不会自动重新调用付费模型。
- 为避免共享 SQLite 时新进程误伤其他进程的活跃任务，只恢复超过配置时间未更新的任务；默认为 900 秒。
- SQLite 为单 Gateway 进程默认实现；调用方只依赖 `JobStore`，后续可替换 Redis/PostgreSQL。

## 内容契约变化

- `development_stages[].historical_period/start_year/end_year` 表示领域历史；`learning_path[].start_week/end_week` 才表示用户学习日程。
- `language` 明确正文语言，论文标题和专业术语可保留英文。任何质量 issue 都使顶层状态至少为 `quality_warning`。
- 问题与子方向增加演进阶段和相互关联 ID，用于前端按发展顺序组织全景。
- 学习步骤增加 `deliverables`；基线实验步骤必须有 `reproducibility_checklist` 和 `evaluation_metrics`。
- `reproducibility` 保留策略版本、检索查询、数据源和最终论文 ID；论文同时返回各排序分量。

## 部署边界

`DOMAIN_ONBOARDING_JOB_DB` 指定 SQLite 路径，`DOMAIN_ONBOARDING_JOB_WORKERS` 控制执行数（默认 2），`DOMAIN_ONBOARDING_JOB_QUEUE_SIZE` 控制等待队列（默认 20）。每个请求者默认最多 2 个活跃任务、每分钟 10 次提交；超限返回 `429` 和 `Retry-After`。终态任务默认保留 7 天，后续提交任务时分批清理。

`DOMAIN_ONBOARDING_JOB_TOKEN_SECRET` 应在生产环境显式设为至少 32 字节随机值。未配置时，单机开发环境会在 SQLite metadata 中创建并持久化随机密钥，确保重启后旧任务令牌仍有效。Docker Compose 已要求生产显式提供此变量。

Docker Compose 已将任务库挂载到独立数据卷。多 Gateway 副本部署前仍必须把 `JobStore` 与执行队列换成 Redis/PostgreSQL 和共享 worker；SQLite 实现只支持单 Gateway 进程。

当前使用任务级 capability token 防止任务 ID 被枚举后查询或取消。项目接入统一身份认证后，还应在 Gateway 层将 token 与真实用户/租户绑定；当前的 IP + 请求元数据仅用于单进程限流，不代替统一鉴权。
